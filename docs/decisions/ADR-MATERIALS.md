## 目的・背景

エコシステムは、**チャンネル**と**素材**の 2 つで組み立てる。チャンネルは、素材を出すかどうか・いつ・どのように出すかを決める（[ADR-CHANNELS](ADR-CHANNELS.md)）。素材は、アプリ利用者に届く中身である。本書は素材の種類と、種類ごとに作る人・責任・確かめ方・届き方を決める。

素材の種類ごとに、次の問題があった。

**素材集**（素材提供者が前もって作る素材）: 素材がチャンネルのパッケージの一部（`channel.json` の `resources`）だけだと、審査も更新もチャンネル単位になる。

1. **審査の重複**: 同じ素材（観光協会の音声ガイドなど）を複数のチャンネルで使うと、チャンネルごとに審査し直す
2. **素材だけの参加ができない**: 観光協会・写真家・語り手は、語り手や話題まで含むチャンネルを作らないと素材を届けられない
3. **更新の波及**: 素材を直すと、使っているチャンネルがすべて申請し直しになる
4. **利用許諾を確かめられない**: その素材を使ってよいかは、チャンネル提供者の自己申告（`license: permission`）でしか示せない

**組み込みの素材**: アプリがすでに使っている素材（AI の解説・話しかけ、Wikimedia Commons のスポットの写真、合成の背景音、雰囲気の絵、定型文）は、どれも「その場で取得・生成する」もので、第三者の素材とは別々の仕組みで動いていた。

**スタジオ**（店などの素材提供者が、決めた場所と期間に出す短いお知らせ）と**一言**（アプリ利用者がその場所に置く投稿）:

1. **だれの発言か**: 一言はアプリ利用者の発言、スタジオは店や地域の発言である。AI の語りと同じ声で読み上げると、だれが言ったのかが分からなくなる
2. **責任者**: 一言は事前に審査しない（運営は当面 1 人。ADR-CHANNELS C-10）。問題のある一言の責任を、だれがどこまで持つかを決める必要がある
3. **置いた人の識別**: 名前を出さなくても、同じ人の一言を場所をまたいでつなげられると、その人の動きが分かる。一方で Google Play のユーザー生成コンテンツのポリシーは、利用規約への同意、通報、ユーザーのブロックを求める
4. **宣伝**: ADR-AI-ROLES H-16 は宣伝をほかの素材と区別しない。スタジオは店の宣伝そのものであり、いずれ有料にする（REQ-STUDIO U-9）
5. **チャンネルとの関係**: チャンネルの外で、チャンネルにかかわらず読み上げると、チャンネルの雰囲気に合わせて選べず、チャンネルのきっかけとも組み合わせられない。アプリの中でも、素材提供者の IF の外の別の道を通る

開発者から次の方針が示された。本書はその決定を記録する。

- 素材（文字・映像・画像・音声）を作る素材提供者の役割をチャンネルから切り出し、チャンネルは素材を利用してアプリ利用者に見せる。組み込みと第三者の素材提供者を、同じインタフェースで扱う
- スタジオは店などが出す素材、一言はアプリ利用者の投稿で、互いに直接の関係はない。どちらもチャンネルに組み込んで使う
- 素材を出すかどうか・いつ・どのように出すかは、チャンネルが決める

## スコープ・非スコープ

スコープ:
- 素材とチャンネル・アプリ・アプリ利用者の役割の分担と、出し方を決める順番
- 素材の種類と、種類ごとの作る人・責任・確かめ方・届き方
- 素材提供者の共通のインタフェース（IF）の大枠
- 素材集の審査・公開・版・利用許諾・取り下げの大枠
- スタジオを出す素材提供者の承認と責任、宣伝との関係
- 一言の置いた人の責任・識別・ブロック
- スタジオと一言をチャンネルで使うときの決まり
- 素材提供者の管理（身元・鍵の移し替え・退会・なりすまし・権利の申し立て）のうち、アプリとリストに関わる方針

非スコープ（別の文書で決める）:
- IF の項目・値・エラーの詳細と、素材集の形式（[API-MATERIALS](../contracts/API-MATERIALS.md)）
- スタジオと一言を置く・配る契約の形（[API-LOCAL-MATERIALS](../contracts/API-LOCAL-MATERIALS.md)）
- リストに素材集を載せる形式（[API-CHANNEL-LIST](../contracts/API-CHANNEL-LIST.md)）
- `channel.json` での素材の書き方（[API-CHANNEL-PACKAGE](../contracts/API-CHANNEL-PACKAGE.md)）
- スタジオと一言の機能・上限・受入条件（[REQ-STUDIO](../requirements/REQ-STUDIO.md)・[REQ-NOTES](../requirements/REQ-NOTES.md)）
- 管理システムのデータモデル・画面（yorisoi-console）
- 素材のテキストを AI の根拠として渡す決まり（[ADR-AI-ROLES](ADR-AI-ROLES.md) H-3〜H-5、API-MATERIALS「AI の根拠」）
- スタジオの有料化（REQ-STUDIO U-9）

## 方針・決定事項

### 素材とチャンネル

| No. | 論点 | 決定 |
|---|---|---|
| D-1 | 役割の分担 | **素材を作る人**は素材を作る（何を: 中身・出典・書き起こし・代替テキスト・何についての素材か・誰に使わせるか）。**チャンネル**は素材を使って見せる（出すかどうか・いつ・どう見せるか: きっかけ・見せ方・候補の順番）。**アプリ**は見せ方の安全の決まり（API-CHANNEL-PACKAGE F-8）と取得の時期（F-10）を強制し、読み上げ・カード・再生を行う。**アプリ利用者**は、設定で受け取る素材を絞る |
| D-2 | 素材の種類 | 5 つ。**組み込み**（アプリのコードで動く。AI の語り・Commons の写真・合成の背景音・雰囲気の絵・定型文）、**素材集**（素材提供者が署名して出す）、**チャンネルに同梱の素材**（`resources`。そのチャンネル専用の素材集として扱う）、**スタジオ**（素材提供者が、決めた区画と期間に出す短いお知らせ）、**一言**（アプリ利用者がその場所に置く投稿）。種類ごとの作る人・責任・確かめ方・届き方は下の表のとおり。役割と責任の上では、AI の語りは素材提供者ではなく実演の層として扱う（ADR-AI-ROLES H-2）。IF 上は組み込みの素材提供者のまま |
| D-28 | 出し方を決める順番 | 素材（どの種類も）を出すかどうか・いつ・どのように出すかは、**チャンネル**が決める。ただし次の内側に限る。① **アプリの方針**: 見せ方の安全（F-8）、止められない出来事（F-4）、上限（AI の 1 日の上限、スタジオと一言の読み上げの上限）、取得の時期と位置の扱い（F-10）、出どころの表示、根拠にしないこと（D-29）。だれも緩められない。② **アプリ利用者の設定**: 受け取る素材を絞るだけで、広げられない（スタジオを聞くか、一言を聞くか、写真を取る回線など）。チャンネルが出さないと決めた素材を、アプリ利用者の設定で出すことはしない。チャンネルに①を書く項目はない（API-CHANNEL-PACKAGE G-5） |
| D-29 | 人の発言の層 | スタジオと一言は「**人の発言**」の層とし、ADR-AI-ROLES の根拠・演出・実演・枠・考査のどれにも入れない。AI の語りの根拠にしない。AI は言い換え・要約・感想を足さず、語り手が出どころを紹介して原文を読み上げる（一言は「この辺りを通った人の一言です。」、スタジオは「〇〇からのお知らせです。」）。アプリの画面でも、AI の発言と分けて出す |
| D-43 | 用語 | 素材の種類の名前は、組み込み・素材集・同梱の素材・**スタジオ**・**一言**。スタジオは 1 件ずつも「スタジオ」と呼ぶ（「スタジオを出す」）。一言はスタジオに含めず、互いに直接の関係はない。スタジオを出すのは素材提供者で、別の役割の名前は作らない（関係者は、アプリ利用者・チャンネル提供者・素材提供者・運営のまま）。アプリ利用者に向けた読み上げと画面では、中身が分かる言い方を添える（「〇〇からのお知らせです」、設定の「スタジオ（店や地域のお知らせ）」） |
| D-3 | 共通の IF | すべての種類の素材提供者を同じ IF で扱う。IF は 3 つの型（素材提供者の記述・素材の要求・素材）と 2 つの操作（準備する・出す）。詳細は [API-MATERIALS](../contracts/API-MATERIALS.md) |
| D-4 | 違いの表し方 | IF の形は分けず、素材提供者の記述の属性（`trust`・`fetch`・`exposure`・`generated`）で表す。何を許すかは、属性を見てアプリの方針が決める。方針はチャンネルからも素材提供者からも変えられない |
| D-16 | 契約と型の置き場所 | IF と素材集の形式は API-MATERIALS に置く。型（記述・要求・素材・参照）は `core-format` に入れ、アプリと管理システムの機械審査で同じ定義を使う |

| 種類 | 素材提供者の ID | 作る人 | 中身の責任 | 運営の確かめ方 | 届き方 |
|---|---|---|---|---|---|
| 組み込み | `builtin:<名前>` | アプリ | 運営（AI の語りは実演の層。ADR-AI-ROLES） | アプリのコードと固定の指示（D-6） | その場で取得・生成 |
| 素材集 | `collection:<素材集のID>` | 素材提供者 | 素材提供者 | 素材集ごとの審査（D-7） | 署名したリストに載せ、前もって取得（D-5） |
| チャンネルに同梱の素材 | `self` | チャンネル提供者 | チャンネル提供者 | チャンネルと一緒に審査（ADR-CHANNELS C-3） | チャンネルのパッケージ |
| スタジオ | `builtin:studio` | 素材提供者（スタジオを出す承認を受けた人） | 素材提供者 | 素材提供者の承認と、載せるたびの自動の確認（D-30） | 区画ごとの一覧で、載せてすぐ（D-42） |
| 一言 | `builtin:note` | アプリ利用者 | 置いた人 | 置く前の自動の確認と、通報（D-32） | 区画ごとの一覧で、置いてすぐ（D-42） |

### 組み込みの素材

| No. | 論点 | 決定 |
|---|---|---|
| D-6 | 組み込みの素材提供者の増やし方 | アプリの更新だけで増やす。その場で外部の API を呼ぶもの・AI で生成するものの安全（回線の条件、共通の指示、出典の表示）は、アプリのコードと固定の指示で守る |

### 素材集

| No. | 論点 | 決定 |
|---|---|---|
| D-5 | 素材集に許すこと | `fetch` は前もっての取得（`prefetch`）だけ、`exposure`（外部に題材が伝わること）はなしだけ。素材提供者が自分の API をその場で呼ばせる形（動的な第三者の素材提供者）は、IF では書けるが方針で禁止する。理由は、その場で取得するとアプリ利用者の位置が相手に伝わること（F-10）と、中身が毎回変わり審査できないこと |
| D-7 | 素材集の審査と公開 | 素材集は、素材提供者が自分の鍵で署名し、チャンネル管理システムに申請する。運営はチャンネルとは別の単位として審査・承認し、承認済みのリスト（API-CHANNEL-LIST）に載せる。素材集を更新したときは、素材集だけを審査し直す（チャンネルは申請し直さない）。審査は無料で、期間の目安はチャンネルと同じ 5 日（ADR-CHANNELS C-14） |
| D-8 | チャンネルが参照する版 | チャンネルは素材集の ID と、使える最低の版を書く。実際に使う版は、運営が署名するリストが決める。公開中のチャンネルが使っている素材の ID を消す・種類を変える更新は、管理システムが受け付けない |
| D-9 | 利用許諾 | 素材提供者は素材集に、使ってよいチャンネルの範囲（誰でも／指定のチャンネル提供者だけ）を書いて署名する。管理システムはチャンネルの申請時に、アプリは取り込み時に、機械で確かめる |
| D-10 | 何についての素材か | 素材には題材（スポット・地点）を付けられる。チャンネルは、素材の ID で選ぶほかに、題材で選ぶこともできる（「このスポットについての素材があれば出す」）。出すきっかけと見せ方は常にチャンネルが決める |
| D-11 | 候補の順番 | チャンネルは 1 つの見せ方に複数の素材提供者を並べられ、アプリは最初に出せたものを使う（例: 観光協会の解説 → なければ AI の解説）。API-CHANNEL-PACKAGE F-12 の `replace`／`add` はこの書き方で表せる |
| D-12 | 素材集が取り下げられたとき | その素材集は「出せない」として扱い、次の候補に進む。候補がなければ、そのきっかけは出さない。チャンネル（語り）はそのまま続ける |
| D-13 | 組み込みのチャンネル | 組み込みのチャンネルも、内蔵のリストに載っていて利用許諾が合う素材集を使える |
| D-14 | アカウント | 素材提供者はチャンネル提供者と同じ鍵とアカウントID（`sg1…`）を使う。1 つのアカウントでチャンネル提供者と素材提供者を兼ねられる。登録・鍵の紐づけ・停止（申請を止めるだけで、公開中のものはそのまま）・操作の記録・メールでの通知は、管理システムのチャンネル提供者の仕組みをそのまま使う |
| D-17 | 素材集の参照と鍵の移し替え | チャンネルは素材集を**素材集の ID だけ**で参照する（素材提供者のアカウントIDを書かない）。素材集の ID はリストの中で一意で、最初に登録した素材提供者が持ち、取り下げ・退会のあとも再利用させない（チャンネルの ID と同じ）。素材提供者が誰かはリストの `collections[].producer` で分かる。鍵の移し替えはアカウント単位で、チャンネルと素材集が一緒に移る。リストには `producerChange` を載せる（API-CHANNEL-LIST P-9 の `publisherChange` と同じ考え方）。参照は ID だけなので、移し替えでチャンネルの参照は壊れない |
| D-18 | 依存の把握と知らせ | 管理システムは、チャンネルの承認時に、どの素材集のどの版・どの素材を参照しているかを記録する。素材集の取り下げ・更新・利用許諾の縮小のときは、使っているチャンネル提供者にメールで知らせる。素材提供者には、自分の素材集を使っているチャンネル（リストに載っているもの）を見せる |
| D-19 | 素材提供者の退会 | 公開中の素材集を自動で取り下げる。使っているチャンネルは次の候補に進むので壊れない（D-12）。権利を持つ人がいない素材を配り続けないため。出しているスタジオも止める |
| D-20 | なりすまし | 誰でも登録できる（ADR-CHANNELS）ため、素材提供者の表示名と素材の出典（`credit`）は名乗りにすぎない。初めての素材集の審査で、運営が、名乗っている団体・個人であることと素材の権利を、登録した連絡先など鍵とは別の経路で確かめる。表示名を変えたときも確かめ直す |
| D-21 | 権利の申し立て | 権利者からの申し立て（無断の利用・なりすまし）を、リストの運営の連絡先（案内文書の `contact`）でメールで受け付ける。管理システムに受け付けの画面は作らない（担当者 1 人で件数が少ないうちは、メールで足りるため）。受け付け → 運営の確認（提供者の言い分も聞く）→ 取り下げ・置き換え・退ける、の流れと目安は審査基準「権利の申し立て」に置く。明らかなときは確認を待たずに取り下げ、繰り返し・なりすましは提供者を停止する。チャンネルにも同じ窓口を使う |
| D-22 | 外部の素材の確認 | 管理システムは毎日の公開の処理で、公開中の素材集の外部の素材（URL）を確かめ、取得できない・ハッシュが合わないときは素材提供者に知らせる。アプリ側では、その素材が「今は出せない」になるだけで、次の候補に進む |
| D-23 | 基準で選ぶ素材提供者 | チャンネルは、具体的な素材集・素材を指す代わりに、選ぶ基準（素材の種類・タグ・言語・長さ）を書ける。基準は「選択の素材提供者」として共通の IF で動き、リストに載っている素材集から基準と題材に合う素材を出す。題材を問わないきっかけ（「寺社・史跡に近づいたら」）と組み合わせて使う |
| D-24 | 基準で選ぶときの前もっての取得 | 素材集に地域（`regions`、geohash の 3 文字。約 150km 四方。管理システムが素材の題材から計算する）を載せ、端末が今いる地域とその隣の地域（9 つ）の素材集だけを、従量制でない回線のときに前もって取得する。地域を持たない素材集（場所に結びつかない素材）は地域を問わない。**F-10 を緩める判断**: 取得の要求から 150km 四方ほどの地域が運営に伝わる。IP アドレスから分かる粗さと同じ程度で、近づいてから取得すること（素材の場所が伝わること）はしない |
| D-25 | タグ | 基準に使うタグは、API-MATERIALS に置く決まった一覧から選ぶ（自由に書けない）。素材提供者が素材に付け、素材集の審査で正しいかを確かめる |
| D-26 | 複数の素材が当たったとき | チャンネルが優先する素材提供者の順番を書ける。書かないときは、確認済みの素材提供者（未決事項 No.4 で印を付ける場合）→ 承認日の新しい素材集の順。同じ散歩では、同じスポットで出す素材を変えない |
| D-27 | 基準で選ぶときの審査 | チャンネルの審査では、どの素材が出るかではなく、基準（タグ・種類・長さ）と、どのスポットで出すかを確かめる。素材は素材集の審査、見せ方の安全はアプリの強制で守る（AI の語りと同じ考え方）。利用許諾（`grants`）がチャンネル提供者を含まない素材集は、基準に合っても使わない |

### スタジオ

| No. | 論点 | 決定 |
|---|---|---|
| D-30 | スタジオを出す人と責任 | 運営は、スタジオ 1 件ずつではなく、スタジオを出す**素材提供者**を審査・承認する。運営は、本人確認、どんな団体・人か、何を出したいか、スタジオの決まりへの同意を見て承認し、違反があれば承認を取り消す。中身の責任は素材提供者が持ち、素材提供者の名前（個人は屋号・活動名でもよい）を必ず出す。載せる前に自動の確認（音声は文字に起こし、運営の AI で確かめる）をし、当たったスタジオは載せずに素材提供者に返す。運営が関わるのは、確認の誤りの申し出、通報、承認の取り消しなどの事後の対応だけ（ADR-AI-ROLES H-12 と同じく、AI の指摘だけでは止めない） |
| D-31 | 宣伝との関係 | ADR-AI-ROLES H-16（チャンネル・素材の宣伝を区別しない）は変えない。スタジオは、**素材提供者の名前を必ず出す**ことで、事業者の表示であることが分かるようにする。無料の間は「広告」とは出さない。有料にするときは「広告」と出し、本書を改める（REQ-STUDIO U-9）。一言での宣伝は置く前の確認で止める（REQ-NOTES） |

### 一言

| No. | 論点 | 決定 |
|---|---|---|
| D-32 | 置いた人の責任と運営の役割 | 一言はアプリ利用者の投稿で、中身の責任は置いた人が持つ。初めて置く前に利用規約に同意してもらい、置いてはいけない一言と、消すこと・締め出すことを示す。運営は場を用意する者として、置く前の自動の確認、通報、自動で隠す、消す、締め出すで守る（ADR-AI-ROLES H-11 の事後の対応と同じ考え方）。事前に人が審査することはしない |
| D-33 | 置いた人の識別 | 置いた人は、運営の AI の中継と同じインストール ID（Play Integrity で確かめた端末。API-AI-RELAY AR-2・AR-3）で識別し、サーバーには HMAC でだけ持つ。名前・アカウント・連絡先は集めない。権利を侵す一言について発信者の情報を求められたとき、出せるのはサーバーにある情報（インストール ID の HMAC、置いた日時、区画）だけで、そのために新しく集めることはしない |
| D-34 | 配る一覧とブロック | 区画の一覧で配る一言には、置いた人を表す値を入れない（一言の ID・文・区画・期限・スポットの名前だけ）。同じ人の一言を場所をまたいでつなげられないようにするため。ブロックと自分の一言の判定はサーバーで行う。聞いた人がブロックすると、サーバーは「ブロックした人の HMAC → 置いた人の HMAC」の組を持ち、一覧を返すときにその人の一言を外す。自分の一言には印を付けて返す。ブロックの組は、解くまで、最長 1 年持つ |

### スタジオと一言をチャンネルで使う

| No. | 論点 | 決定 |
|---|---|---|
| D-35 | 素材提供者の種類と属性 | スタジオと一言は、**組み込みの素材提供者** `builtin:studio`・`builtin:note` にする。中身は運営の配信（API-LOCAL-MATERIALS）から取る。素材集にはしない（案 P）。「組み込み」は IF の上の種類（アプリのコードが取りに行く）を表すだけで、作る人・責任を持つ人ではない（D-2 の表のとおり。AI の語りが IF の上では組み込みでも、役割は実演の層であるのと同じ）。属性は `trust=builtin`・`generated=false`。取得は区画（geohash6、約 1.2 km × 0.6 km）ごとの一覧で、取りに行く要求から区画が運営に伝わる。これを表す `exposure` の値 `area` を足す |
| D-36 | きっかけ | チャンネルは、ほかの素材と同じく `cues` で出し方を書く。出来事 **`idle`**（語りの合間。アプリが、話すことがないと決めたとき）を使える。`idle` では、端末がいる区画とその周りのスタジオ・一言から選ぶ。`spot`・`point` のきっかけでは、そのスポット・地点の区画のスタジオ・一言から選び、AI の解説の後に出す |
| D-37 | チャンネルが決められること | 出すかどうか、どのきっかけで出すか、どれを出すか（スタジオか一言か、スタジオの**分類**）、前置き（D-40）。スタジオには分類を付ける（素材提供者が、決まった一覧から選ぶ）。一言には分類がない |
| D-38 | チャンネルが変えられないこと | D-28 ①のうち、スタジオと一言では次のとおり。原文を出どころとともに読み上げる（D-29）。根拠にしない・言い換えない・要約しない。アプリ利用者の設定（スタジオを聞くか、一言を聞くか）。読み上げの上限（1 時間にスタジオ 2 件・一言 10 件、同じスタジオは 1 日 1 回、同じ一言は 1 回）はアプリ全体で数える。取得は区画の一覧だけ |
| D-39 | スタジオ・一言を書かないチャンネル | 省略形として、`idle` でスタジオと一言を出すことに展開する（D-15 と同じ考え方）。チャンネルは、止める・絞る・別のきっかけで出すを書ける。組み込みのチャンネルも同じ |
| D-40 | 前置き | チャンネルは、出どころの紹介の前に置く**前置き**を、アプリが決めた文の一覧から選べる（例「ところで、近くでお知らせがあるみたい。」）。AI に作らせない。出どころの紹介（D-29）は省けない |
| D-41 | 責任と審査 | チャンネル提供者は、スタジオ・一言の中身に責任を持たない（自分が素材提供者として出したスタジオを除く）。チャンネル提供者は、1 件ずつ選ばず、出す条件だけを決める。チャンネルの審査では、出す条件（きっかけ・分類・前置き）を確かめ、どのスタジオ・一言が出るかは確かめない（D-27 と同じ考え方）。聞いた人の通報は、チャンネルではなく運営に届く |
| D-42 | 配信の契約と置き場所 | スタジオと一言を置く・配る契約は **API-LOCAL-MATERIALS**（その場の素材）にする。区画ごとに 1 回の要求でスタジオと一言の両方を返す（要求の回数と、区画から伝わる情報を少なくするため。スタジオと一言に関係があるからではない）。認証は API-AI-RELAY のセッション（同じトークン）を使い、サーバーは yorisoi-console のスタックに置く。API-SECRET-MESSAGES 第 2 版の `public` は使わない |

## 判断テーマ

アプリ利用者に届く中身を、チャンネルから切り分けた「素材」として扱うか。扱うなら、素材の種類ごとに、だれが作り、だれが責任を持ち、運営がどう確かめ、どう届けるか。チャンネルにはどこまで出し方を決めさせるか。

## 採用案と採否理由

案 C・案 F・案 H・案 K・案 N・案 P・案 R・案 T・案 W を採用する。

- 素材集を独立した単位にすることで、役割の分離の効果（再利用・素材だけの参加・素材の更新が波及しないこと）が得られる。利用許諾を素材提供者の署名で示すので、アプリと管理システムが機械で確かめられる
- 共通の IF で、その場で取得・生成する素材、素材集、スタジオ、一言を、チャンネルから同じ書き方で使える
- スタジオと一言を人の発言の層にすれば、AI の役割と責任の決まり（ADR-AI-ROLES）を変えずに済み、だれの発言かも聞く人に分かる
- スタジオは、素材提供者の言葉を AI が手を加えずに読み上げるので、だれが言ったかが分かれば、中身は出した人の責任にできる。運営が素材提供者を承認すれば、運営 1 人で回り、今のお知らせも間に合う
- 一言は、一覧に置いた人の値を入れなければ、人の動きをつなげられない。ブロックはポリシーで求められるので、サーバーで持つ。インストール ID と Play Integrity は運営の AI で使っていて、締め出しと上限（1 日 10 件）をそのまま端末ごとにかけられる
- スタジオと一言を組み込みの素材提供者にすれば、原文と出どころ・根拠にしないことを、チャンネルから変えられない方針として守ったまま、チャンネルに出し方だけを任せられる。書かないチャンネルは省略形で今と同じに届く
- 出し方を決める順番を 1 つにすれば、どの種類の素材にも同じ考え方がかかり、新しい種類を足すときも D-2 の表に 1 行足すだけで済む

却下した理由:
- 案 A・案 B: 素材集の問題 1〜4 が残る（案 B は利用許諾を名乗れるだけ）
- 案 D: 素材集を直すと、使うチャンネルすべてが申請し直しになる。同じ素材の審査も重複する
- 案 E・案 V: 人の発言が AI の発言として事実になる。宣伝が語りに紛れ込む
- 案 G・案 Q: 運営 1 人では回らず、今のお知らせが間に合わない
- 案 I: 承認待ちで今のお知らせが遅れる。責任が 2 段に分かれる
- 案 J: 一覧から同じ人の一言をつなげられる
- 案 L: Google Play のポリシーに合わない
- 案 M: 作る量が多く、名前を出さない一言と合わない
- 案 O: チャンネルに合わせて出せない
- 案 S: スタジオの届く範囲が、チャンネルの書き方しだいで狭くなる
- 案 U: 前置きで出どころをぼかせる。チャンネルの審査で文を見る手間が増える
- 案 X: 原則に例外ができる。アプリ利用者が聞きたいなら、スタジオを出すチャンネル（組み込みのチャンネルなど）を選んでもらう

利点:
- 観光協会・写真家・語り手が、チャンネルを作らずに素材を届けられる。店や地域は、スタジオで今のお知らせを届けられる
- 運営は同じ素材を一度審査すればよい
- チャンネルは「観光協会の解説があればそれ、なければ AI」「寺社の催しのスタジオだけ」のように、素材を組み合わせ・選んで出せる

注意点:
- 審査の単位が 2 つ（チャンネルと素材集）になり、管理システムの申請・審査・取り下げの仕組みが倍近くになる
- 素材集の取り下げ・更新が、それを使うチャンネルに波及する（D-8・D-12 で抑える）
- 審査はチャンネルと素材集の組み合わせを見ない。素材集が更新されたとき、チャンネルの見せ方と合わなくなるおそれがある（D-8 の範囲の外の、内容の変化）
- チャンネルはスタジオを「出さない」とも書けるので、そのチャンネルを使う人にはスタジオが届かない。素材提供者向けの手引きに書く
- `idle` は、上限（D-38）と語りの後に置く間の中で出す。チャンネルが `idle` を何度書いても、上限より多くは出ない
- アプリを入れ直すとインストール ID が変わり、一言の締め出しと 1 日の上限を逃れられる（REQ-NOTES）。Play Integrity で端末の確認はするが、同じ端末かまでは分からない
- 一言のブロックの組がサーバーに残る。HMAC だけで持ち、ログに書かない
- API-SECRET-MESSAGES 第 2 版の `public` の `event`・`notice` と、スタジオの役目が重なる。秘密メッセージを実装するときに、`public` を残すかを決める

見直しの条件:

- 動的な第三者の素材提供者（その場で取得する素材）の要望が出たとき（D-5。位置を伝えずに取得する方法と、審査の方法を考える）
- 素材集の取り下げ・更新でチャンネルが壊れる問題が実際に起きたとき（D-8・D-12）
- 素材集の利用に対価が生じる、または素材提供者とチャンネル提供者の取り決めをシステムで扱う必要が出たとき
- 基準で選ぶ素材集が増え、地域ごとの前もっての取得（D-24）が通信量・保存の量の上限に収まらなくなったとき。また、地域が伝わることへの懸念が出たとき
- スタジオを有料にするとき（D-31）
- 多くのチャンネルがスタジオを止め、素材提供者にとっての価値が下がったとき（D-39）

## 制約

- F-8（見せ方の安全）・F-10（取得の時期）・F-11（出典と代替）・F-13（話す順番）は、素材の種類にかかわらず変えない。ただし基準で選ぶ素材提供者の前もっての取得は地域単位（D-24）、スタジオと一言の取得は区画単位（D-35）にする
- 組み込みの素材提供者が外部の API を呼ぶとき（Commons の写真、AI）は、題材（スポットの名前・ID）が外部に伝わる。回線の条件とアプリ利用者の設定で抑える
- 素材集の中身は機械では確かめられず、人の審査に頼る（API-CHANNEL-PACKAGE の制約と同じ）
- 運営は当面 1 人（ADR-CHANNELS C-10）
- 位置は区画より細かく送らない（API-CHANNEL-PACKAGE F-10 の考え方）
- 運営の AI は Bedrock を東京で使う（ADR-AI-RELAY R-5）
- 知らない値で制限が緩まない（API-CHANNEL-PACKAGE G-5）。`idle` や `builtin:studio`・`builtin:note` を知らないアプリは、そのきっかけ・候補を使わない

# yorisoi 文書体系の再設計

## 状態

設計内容はユーザーレビューで承認済み（2026-10-17）。

## 目的

yorisoi のエコシステム方針と、SanpoGuide 固有の実装・運用情報が同じ文書群に混在している状態を改める。文書の入口、分類、用語、正本の関係を整理し、読者が「どのアプリにも当てはまる約束」と「SanpoGuide で現在有効な手順」を区別できるようにする。

## 現状と問題

- ADR-003 は yorisoi を複数の付き添いアプリを支える共通基盤と定めている。
- 一方、関係者文書、審査基準、API-004、および運用手引きには SanpoGuide 固有の対象、機能、画面、公開状態が混在している。
- `docs/README.md` はリポジトリの役割を説明するが、読者がエコシステム共通文書と SanpoGuide 固有文書を素早く区別する入口としては不十分。
- 番号だけの ADR/API 参照は、リポジトリをまたぐと対象を特定しにくく、移動後の旧リンクも維持する仕組みが必要。

## 合意した設計

### 1. 文書の分類

`docs/` を次の役割に分ける。

| 分類 | 想定する内容 |
|---|---|
| `overview/` | yorisoi の目的、構成、共通用語、アプリと各リポジトリの関係 |
| `decisions/` | エコシステムの意思決定記録（ADR） |
| `contracts/` | アプリ・管理システム・外部サービスの間で守る技術契約（API） |
| `policies/` | 審査などの運用方針 |
| `apps/sanpoguide/` | SanpoGuide の利用・試用・運用手順と、その時点の公開状態 |
| `work/` | エコシステム全体に関する未完了作業と検討事項 |

OpenAPI など機械処理される契約資産は、既存の検証手順と利用箇所を確認したうえで配置を決める。Markdown 文書と一緒に動かす場合は、参照先を更新し旧パスの案内も用意する。

### 2. 正本と用語

文書の権威の順序を明示する。

1. 承認済み ADR: エコシステムの方針・決定
2. API 契約: システム境界の形式・振る舞い
3. ポリシー: 方針に基づく審査・運用の基準
4. ガイド: 特定の読者が操作・運用するための手順
5. TODO: 未完了作業。決定済みの仕様の正本にはしない

共通文書では、次の概念を区別して表す。

- **yorisoi**: 付き添いアプリとその共通基盤からなるエコシステム
- **yorisoi-platform**: 共通ライブラリを提供するリポジトリ
- **アプリ**: エコシステムを利用する個々のアプリ。SanpoGuide は最初のアプリ
- **yorisoi-console**: チャンネル等の審査・配信を担う管理システム
- **アプリ利用者**: 共通文書で使う利用者の呼び方。散策を行う場合に限り、SanpoGuide 固有文書では「散策者」と呼ぶ

共通方針はアプリ非依存の表現にし、画面名、バージョン、公開状態、URL などの実装・運用事実は SanpoGuide 固有と明記する。現況値には確認時点または更新日を付ける。コードやデータ形式上の既存識別子（`publisher` など）は変更しない。

### 3. 文書 ID と旧リンク

新しい canonical ID は文書種別と主題を組み合わせた意味ベースにする。

| 旧 ID | 新 canonical ID |
|---|---|
| ADR-001 | `ADR-CHANNEL-CURATION` |
| ADR-002 | `ADR-MATERIAL-PRODUCERS` |
| ADR-003 | `ADR-ECOSYSTEM-PLATFORM` |
| ADR-004 | `ADR-AI-ROLES` |
| API-001 | `API-SECRET-MESSAGES` |
| API-002 | `API-CHANNEL-LIST` |
| API-003 | `API-CHANNEL-PACKAGE` |
| API-004 | `API-MATERIAL-PRODUCER` |

旧番号 ID と旧ファイルパスは移行表に記録する。移動元には案内ページを残し、新しい正本と旧 ID の対応を示す。既存の外部参照を探せる範囲で調べ、platform 内リンクをすべて更新する。外部リポジトリの編集は対象外とし、旧 URL から案内を読める状態にする。旧見出しへのフラグメントリンクは自動転送されないため、重要なアンカーは案内ページに互換見出しまたは直接リンクを用意する。

### 4. 内容の扱い

- 全 Markdown 文書をレビュー対象とし、新しい分類に沿って移動・改名・編集する。
- エコシステム共通の説明と SanpoGuide 固有の説明を分離し、重複する説明は正本へのリンクに置き換える。
- 合意済みの技術的決定を、文章の統一を理由に変更しない。
- ADR と契約の間に未解決の矛盾が見つかった場合、推測で一方を選ばず、変更候補と影響をレビュー事項として示す。
- API/ADR の旧番号と新 ID の対応表を保ち、文書相互参照と識別可能性を維持する。

## 対象範囲

### 対象

- `yorisoi-platform/docs/` にあるすべての Markdown 文書
- 対象文書間の相互リンク、リンク先見出し、一覧、旧パス案内
- 文書内の表現で説明される ADR/API ID の相互参照

### 対象外

- `yorisoi-sanpoguide`、`yorisoi-console`、`yorisoi-tutorial` のファイル編集
- アプリ、管理システム、ライブラリのコード変更
- API の形式や実装の動作を変える仕様改訂
- 未承認の関係者対応案など、未決事項そのものの承認

## 受け入れ条件

1. `docs/README.md` から、エコシステム概要、決定、契約、方針、SanpoGuide 手引き、TODO の各読者向け入口が分かる。
2. 各文書に、その対象システム・読者・文書状態が必要な範囲で明記され、共通事項とアプリ固有事項を誤認しない。
3. 共通文書の利用者・アプリ呼称と、SanpoGuide 固有文書の「散策者」等の用語が意図的に使い分けられている。
4. 決定・契約・方針・手順・TODO の正本が互いに区別され、重複記述に矛盾がない。
5. 各移動文書に旧 ID・旧パスからの案内があり、platform 内の相互参照が新しい正本に更新されている。
6. Markdown の相対リンクとフラグメントを検証し、未解決の参照があれば一覧化する。
7. 実装事実の変更や文書間の未解決仕様矛盾を、確認なしに解決した形で記述しない。

## 検証

- リポジトリに既存の Markdown リンク検査手段があれば利用する。なければ、Windows 環境で実行可能な最小の一時検査を用い、依存関係やプロジェクト設定は追加しない。
- 文書 ID・旧パスの移行表と、旧パス案内ページの対応を確認する。
- `docs/` 内の相対リンクとフラグメントを検査し、修正または未解決一覧を確認する。
- 文書のみの変更なので、アプリのビルド・テストは実行しない。

## 設計上の判断

- **全面的な情報再設計を選ぶ。** 入口だけの改訂では、エコシステム共通とアプリ固有の混同が他文書に残る。
- **意味ベースの ID を選ぶ。** 新規文書の追加や順番の変更で ID の意味が変わらない。
- **互換案内ページを選ぶ。** GitHub Markdown には移動元からの自動転送がなく、旧パスを外部から参照している可能性がある。
- **仕様の改訂を別判断にする。** 情報構成の変更が既存の技術契約や合意事項を暗黙に変えないようにする。

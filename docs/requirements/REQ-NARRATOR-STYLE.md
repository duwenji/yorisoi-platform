# 語り手の型 要件定義

## 文書情報
| 項目 | 内容 |
|---|---|
| 文書ID | REQ-NARRATOR-STYLE |
| ドキュメント種別 | 要件定義書 |
| 対象システム/機能 | アプリ利用者が、語り手の性格の「型」（ユーモア多め・物知りなど）を設定で選べるようにする。チャンネルは使ってよい型を決められる。platform core-format・API-CHANNEL-PACKAGE、yorisoi-sanpoguide、yorisoi-cycleguide、yorisoi-console（validator） |
| 承認者 | 開発者（duwenji） |
| ステータス | 承認済（2026-11-21） |

## 目的・背景

語り手の人格は、今はチャンネルの `guide/persona`・`companion/persona`（立場と口調、各 600 字）の自由な文章だけで決まります。標準のチャンネルの散歩の友は「気心の知れた友だちです」の 1 行で、性格と呼べる中身がありません。アプリ利用者は、チャンネルを選ぶ以外に、語り手の性格に手を入れられません。

本書は、アプリ利用者が設定で語り手の「型」を選べるようにし、同じチャンネルでも、ユーモアの多い語り手や、物知りな語り手で聞けるようにする要件です。型はアプリが用意した決まった言い回しでプロンプトに入れ、チャンネルの演出（語り手・話題）の上に味付けとして重ねます。チャンネルの雰囲気を崩さないよう、チャンネルは使ってよい型を決められます。

## スコープ・非スコープ

### スコープ
- 型の一覧と、型ごとのプロンプトの固定部分（両アプリ）
- チャンネルが使ってよい型を書く項目（core-format・API-CHANNEL-PACKAGE）
- 設定画面で型を選ぶこと、チャンネルが許さない型のときの扱い（両アプリ）
- 開発者の記録に型を残すこと、validator の見本
- 文書の追従: 利用者の手引き・チャンネル提供者の手引き・技術チュートリアル

### 非スコープ
- 計画性（話の流れを組む・先回りして段取りを提案する）。別の要件で検討する（U-1）
- 項目ごとの度合い（ユーモア 1〜3 など）を利用者が組み合わせること。型から 1 つ選ぶだけにする（D-1）
- 利用者が自由な文章で性格を書くこと
- チャンネルが独自の型を足すこと（チャンネルは今の `persona` で書く）
- 話しかけの頻度・解説の長さを型で変えること（今の `talk.level`・`guide.length` と設定のまま）
- 声（読み上げの声色・速さ）を型で変えること
- iOS

## 方針・決定事項
| ID | 決定 | 理由 |
|---|---|---|
| D-1 | アプリ利用者は、アプリが用意した型から 1 つ選ぶ。既定は「おまかせ」（チャンネルの語り手のまま） | 設定が簡単。型ごとの言い回しをアプリが持つので、どの型も同じ枠（AI-ROLES H-6）で確かめられる |
| D-2 | 型は、チャンネルの `persona` を置き換えず、その上に重ねる味付けとする。立場（友だち・語り部など）はチャンネルが決め、型は話しぶり（冗談の多さ・豆知識の多さ・気づかいの多さ）だけを変える | チャンネルの演出（AI-ROLES H-1）を利用者が壊さない |
| D-3 | チャンネルは、使ってよい型を並べられる。書かなければ、すべての型を使ってよい。利用者が選んだ型をチャンネルが許さないときは、そのチャンネルでは「おまかせ」で話す | 厳かな寺社のチャンネルなどで、ユーモアの型を外せる。今あるチャンネルは書き直さずに使える |
| D-4 | 型のプロンプトは、アプリの固定部分（枠）に置く。チャンネルから書き換えられない。ユーモアの型にも、からかわない・事実を曲げない決まりを付ける（F-10） | 冗談は、人・地域・信仰を傷つけやすい。固定部分にすれば、アプリ開発者が直す（AI-ROLES H-7） |
| D-5 | 安全の知らせ（天気の急変・日の入り・施設の案内）と、人の発言の素材（MATERIALS D-38）には型を使わない | 知らせは伝わることが先。人の言葉は原文のまま読む |
| D-6 | 両アプリで同じ型の一覧を使う。言い回しは、アプリごとの場面（歩く・自転車）に合わせて書く | 型の名前と意味を両アプリでそろえる |

## 機能要件

### 型の一覧
| ID | 要件 |
|---|---|
| F-1 | 型は次の 4 つ。ID は契約に書く英字。① `default` おまかせ（チャンネルのまま。プロンプトに何も足さない） ② `humor` ユーモア多め（軽い冗談・言葉遊び・明るい相づちを 1 回の発言に 1 つまで） ③ `scholar` 物知り（由来・言葉の意味・豆知識を 1 つ多めに添える。落ち着いた話しぶり） ④ `gentle` やさしい（気づかい・ねぎらいを多めに、穏やかな話しぶり） |
| F-2 | 型ごとの言い回しは、プロンプトの共通部品 `shared/styles/{ID}.md` に置く（両アプリの `prompts`）。`default` のファイルは置かない |

### チャンネルの項目（API-CHANNEL-PACKAGE の変更）
| ID | 要件 |
|---|---|
| F-3 | チャンネルに `narrator.styles`（文字列の配列、任意）を足す。値は F-1 の ID（`default` を除く）。書かなければ、すべての型を使ってよい。空の配列なら、型を使わない（いつも「おまかせ」） |
| F-4 | 知らない ID は無視する（あとで型を足しても、古いアプリでチャンネルが出なくならない）。validator は、知らない ID を警告にする |

### 設定と画面（両アプリ）
| ID | 要件 |
|---|---|
| F-5 | 設定画面の「チャンネル」の欄に「語り手の型」を足し、F-1 の 4 つから 1 つ選ぶ。型ごとに 1 行の説明と、短い話しぶりの例を出す |
| F-6 | 今のチャンネルが許さない型には「このチャンネルでは使えません（おまかせで話します）」を出す。選ぶことはできる（チャンネルを変えると効く） |
| F-7 | チャンネルの一覧・チャンネルの説明に、そのチャンネルで使える型を出す（すべてのときは出さない） |
| F-8 | 型は端末に残し、散歩・走行の途中で変えたら、次の発言から効く |

### プロンプト（両アプリ）
| ID | 要件 |
|---|---|
| F-9 | 解説（`guide/system`）と散歩の友（`companion/system`）の `# 役割` で、チャンネルの `persona` のあとに `## 話しぶり` として型の言い回しを入れる。使う型は、利用者の型をチャンネルが許すならその型、許さなければ `default` |
| F-10 | すべての型の言い回しに、次の決まりを入れる: チャンネルの語り手の立場と口調は変えない / 人・地域・信仰・体・名前をからかわない / 冗談のために事実を変えない・作らない / 型の名前（「ユーモアの型」など）を口にしない |
| F-11 | 安全の知らせ・人の発言の素材（D-5）、振り返り（終わりのまとめ）には、型を入れない（U-3） |
| F-12 | 型を入れた分の字数は、スロットの上限（API-CHANNEL-PACKAGE、合計 4,000 字）に数えない。型の言い回しは 1 つ 200 字以内とする |

### 記録・審査
| ID | 要件 |
|---|---|
| F-13 | 開発者の記録の AI の呼び出しに、使った型の ID を残す |
| F-14 | validator は、チャンネルが許す型ごとに解説と雑談の見本を話させ、審査の画面で型ごとに並べる |
| F-15 | 散歩・走行の記録（履歴）には型を残さない |

### 文書の追従
| ID | 要件 |
|---|---|
| F-16 | API-CHANNEL-PACKAGE に `narrator.styles` と、プロンプトの組み立て方の `## 話しぶり` を足す。両アプリの prompts.md・利用者の手引き・チャンネル提供者の手引き・技術チュートリアルを追従させる |

## 非機能要件
| ID | 内容 |
|---|---|
| N-1 | AI の費用: 型の言い回しで、1 回の呼び出しの入力が 200 字ほど増える。出力の字数の上限は変えない |
| N-2 | 互換: `narrator.styles` を読めない古いアプリは型を使わずに話す（今と同じ）。チャンネルの必要な版（API-CHANNEL-LIST P-20）は上げない |

## 受入条件
1. AC-1（F-1・F-9）: 同じチャンネル・同じスポットで、`humor` と `default` の見本を比べ、`humor` に冗談が 1 つあり、語り手の立場と口調が変わらないと開発者が感じる
2. AC-2（F-3・D-3）: `narrator.styles: ["scholar"]` のチャンネルで型を `humor` にすると、プロンプトに型が入らない（テスト）。設定画面に F-6 の文が出る
3. AC-3（F-4）: `narrator.styles` に知らない ID があるチャンネルが一覧に出て、知る ID の型は使える（テスト）
4. AC-4（F-10）: validator の見本で、`humor` の型の話に、人・地域・信仰をからかう言葉と、与えた情報にない事実がない
5. AC-5（F-11・D-5）: 天気の急変・日の入り・施設の案内・人の発言の素材・振り返りのプロンプトに型が入らない（テスト）
6. AC-6（F-8）: 散歩の途中で型を変えると、次の解説から変わる（エミュレータ）
7. AC-7: 実機で `humor`・`scholar`・`gentle` で歩き、それぞれの違いが分かり、うるさすぎない・押し付けがましくないと開発者が感じる

## 用語定義
| 用語 | 意味 |
|---|---|
| 型 | アプリが用意した、語り手の話しぶりの味付け（F-1） |
| おまかせ | 型を足さず、チャンネルの語り手のまま話すこと |

## 制約
| 種類 | 内容 | 本書での扱い |
|---|---|---|
| AI-ROLES H-1 | 演出はチャンネル提供者が受け持つ | 型は話しぶりだけを変え、チャンネルが許す範囲に限る（D-2・D-3） |
| API-CHANNEL-PACKAGE の互換 | 項目を足すのは互換の変更 | `narrator.styles` は任意の項目（F-3） |

## 未決事項・リスク
| ID | 内容 | 対応 |
|---|---|---|
| U-1 | 計画性（話の流れを組む・先回りして段取りを提案する）。プロンプトだけでは作れず、散歩の始めに流れを組んで覚えておく仕組みが要る | 別の要件で検討する |
| U-3 | 振り返りにも型を入れるか | 見本で比べて決める |
| R-1 | ユーモアの冗談が、場所によっては不謹慎になる（墓地・慰霊碑・事故の跡など） | F-10 に加え、`humor` では、墓地・慰霊の場所の解説で冗談を言わない決まりを入れる。validator の見本で確かめる |
| R-2 | 型がチャンネルの語り手と合わず、ちぐはぐに聞こえる | D-3 でチャンネルが外せる。見本（F-14）でチャンネル提供者が確かめる |
